# Darkphish 0.8 - Campaign Engine 2.0

## Objective

Turn the existing campaign capability into a predictable, schedulable and automatable campaign engine suitable for continuous authorized security-awareness programs while preserving all Darkphish security boundaries and v0.7 compatibility.

## In scope

### DP-080 Campaign lifecycle
Define an explicit campaign state machine with valid transitions and durable audit evidence. At minimum cover draft/scheduled/running/paused/completed/cancelled states as appropriate to the existing model.

### DP-081 Scheduling
Support future campaign start scheduling with clear timezone semantics and validation. Persist canonical timestamps consistently and render them correctly for administrators.

### DP-082 Recurrence
Support bounded recurring campaign policies suitable for authorized awareness programs. Recurrence must be deterministic, inspectable, pausable and cancellable.

### DP-083 Delivery windows
Allow bounded randomized distribution of campaign sends within an administrator-defined delivery window. This is for load spreading and realistic awareness scheduling, not mail-filter bypass or defensive evasion.

### DP-084 Targeting
Target static groups and compatible Smart Groups. Support explicit exclusions and deterministic recipient resolution. Preserve a campaign recipient snapshot/evidence sufficient for audit and reproducibility.

### DP-085 Clone
Clone an existing campaign into a new draft without copying runtime results or mutable execution state.

### DP-086 Pause/resume/cancel
Provide safe idempotent administrative controls with explicit authorization and audit events. Define behavior for already queued/in-flight work.

### DP-087 Preview and test send
Allow administrators to preview campaign composition and send a controlled test only to explicitly selected authorized test recipients.

### DP-088 Template version evidence
Campaign execution must retain enough template/version identity to explain exactly what content/configuration was used even if a template is later edited.

### DP-089 Synthetic test mode
Provide a clearly labelled mode for QA/staging that uses synthetic/test data and cannot be mistaken for a production campaign.

## Out of scope

- Mail-filter bypass or allow-list circumvention automation
- Anti-sandbox/anti-analysis behavior
- Anti-detection or defensive-evasion mechanisms
- Credential replay, stuffing, spraying or external validation
- Multi-tenancy (v0.17)
- AI generation (v0.15)
- Full training engine (v0.9)
- New container/Docker product scope

## Compatibility

- Preserve existing credential safety modes and encrypted-review behavior.
- Raw submitted credentials never enter scheduler/recurrence/targeting/audit payloads.
- Maintain SQLite, MySQL and PostgreSQL support.
- Schema changes use the project's established Goose migration discipline.
- Existing v0.7 data must remain migratable without destructive reset.

## Security requirements

- Every mutating campaign operation requires the existing authorization model and emits durable audit evidence.
- Scheduler workers must be safe under retries and multi-instance execution; no duplicate campaign execution from ordinary retry/race conditions.
- Recurrence and delivery-window inputs are bounded to prevent resource exhaustion.
- Recipient resolution is deterministic and avoids cross-group leakage.
- Test-send cannot silently broaden recipients.
- API/UI state transitions enforce the same server-side rules.

## Performance expectations

Design queries and workers so large recipient sets do not require unbounded memory or unbounded database queries. Add targeted scale coverage around scheduling, recipient resolution and worker claiming.

## Testing

During implementation run targeted package/module tests first. Before merge/release run the complete protected suite including race/static/vulnerability checks and all supported database suites. Add integration tests for state transitions, recurrence, timezone handling, idempotency, multi-instance claiming, pause/resume/cancel, deterministic recipient resolution and migration compatibility.

## Release gates

1. All DP-080 through DP-089 acceptance criteria implemented or explicitly deferred with documented reason.
2. Normal code review completed and findings resolved.
3. Final security review completed and findings resolved.
4. Zero unresolved release-blocking CodeQL findings.
5. Full protected CI/database matrix passes.
6. Upgrade from released v0.7.0 verified.
7. Published native artifacts/checksums/SBOM verified before v0.9 begins.

## Token-efficient implementation protocol

- Treat this file and canonical architecture/security docs as authoritative context.
- Work one DP task or a tightly coupled batch at a time.
- Search for relevant symbols/files before broad repository exploration.
- Read only code required for the current task unless a cross-cutting invariant requires more.
- Run targeted tests during iteration; full protected suites run at integration/release gates.
- Avoid repeated architecture rediscovery; record durable decisions as docs/ADR entries when a new architectural decision is actually made.
- Use one implementation pass, targeted verification, one normal review/fix cycle and one final security review unless evidence requires additional review.
